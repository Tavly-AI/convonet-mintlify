## What are Agent Workflows?

**Agent Workflows** allow you to aggressively automate actions *outside* of the active conversation. You configure logic graphs that execute before the AI agent speaks its first word (Pre-Call/Pre-Chat) or immediately after the session safely concludes (Post-Call/Post-Chat).

Functions execute as strict dependency graphs, meaning independent tools fire simultaneously in parallel, while dependent functions natively wait for upstream data.

## When do you use Pre-Call vs. Post-Call?

You strictly use Pre-Call functions to arm the agent with required context before the interaction begins, and Post-Call functions to log data to external systems after the interaction ends.

**Use Pre-Call (or Pre-Chat) to:**
* **Greet callers by name:** Instantly lookup the caller's phone number in a CRM.
* **Load account context:** Pull active support tickets or billing statuses so the agent knows precisely why they are calling.

**Use Post-Call (or Post-Chat) to:**
* **Log outcomes:** Write the AI summary and sentiment directly into a CRM timeline.
* **Create follow-ups:** Automatically generate callback tickets or SMS notifications.

<Note> **Mid-Call Tools:** If the agent needs to fetch data *during* the active conversation (e.g., checking calendar slots mentioned by the caller), you must use [Integration Tools](/build/single-multi-prompt/integration-tools) instead of Workflow functions.</Note>

## What types of functions are available?

Both workflow slots natively accept four powerful function architectures. 

| Function Type | Description | Availability |
| --- | --- | --- |
| **Integration Tool** | A pre-built tool from a provider (Salesforce, HubSpot, Zendesk, Cal.com). | Pre & Post (All channels) |
| **Custom Function** | A direct HTTP webhook request to your own proprietary endpoint. | Pre & Post (All channels) |
| **Code Execution** | Isolated Javascript executed in Tavly's secure sandbox. | Pre & Post (All channels) |
| **SMS Notification** | Dynamically generated text message based on the call transcript. | Post (Voice only) |

## How do you build a Workflow graph?

You assemble functions sequentially or in parallel directly from the agent's **Workflow** tab, explicitly mapping output data downstream via dynamic variables.

## How do you pass data between functions?

You strictly pass data down the dependency chain by converting a function's raw JSON output into a **Dynamic Variable**.

On a function's **Output** tab, explicitly assign a response field to a dynamic variable name. Any sequentially downstream function can now aggressively reference that precise output as `{{your_variable_name}}`.

Variables become usable as soon as the graph produces them, so a function can only ever see output from something that finished before it. The dashboard enforces this same rule as you're editing — when you pick a variable, it only offers outputs from functions this one actually depends on, not siblings running alongside it or functions that come later.

Two more details worth knowing about how this data reaches the agent:

* **The full result lands in the agent's context**, not just whatever variables you happened to name. Every tool call gets woven directly into the transcript the LLM reads, arguments and response both — what a workflow function actually changes is *where* it lands. A pre-conversation call gets prepended, so the agent has it from its very first turn. Responses are capped at 30,000 characters for an integration tool, and 15,000 for a custom function or code tool (as of August 2026). Use **Select fields** on the **Output** tab to only pass through what matters, rather than letting a huge provider payload crowd out the rest of the prompt.
* **Dynamic variables are pulled from the raw response**, before any of that field selection happens. Narrowing what the agent actually sees never breaks a variable you've already mapped.

If a `{{variable}}` referenced in an input has no value — either because the function it came from never ran, or it returned nothing for that field — the input simply gets left out. If that input happened to be required, the whole function gets skipped rather than sent with a gap in it.

### Variables Available to Post-Conversation Functions

Post-call and post-chat functions run after [Post Call Extraction](/features/post-call-analysis-overview) completes, so on top of everything else, they can also read its results:

| Voice                            | Chat                             | What it holds                                                                                            |
| ----------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `{{call_summary}}`                  | `{{chat_summary}}`                    | The analysis summary                                                                                             |
| `{{call_successful}}`               | `{{chat_successful}}`                 | Whether the analysis judged the session successful                                                               |
| `{{user_sentiment}}`                | `{{user_sentiment}}`                  | The user's sentiment                                                                                              |
| One per custom analysis field       | One per custom analysis field         | Named after the field, coming from your [Post Call Extraction](/features/post-call-analysis-overview) setup      |
| `{{disconnection_reason}}`          | `{{disconnection_reason}}`            | Why the session ended — see [call disconnect reasons](/reliability/debug-call-disconnect)                        |
| `{{call_status}}`                   | `{{chat_status}}`                     | The session's final status                                                                                        |

These only exist for post-conversation functions — nothing earlier in the flow can read them, since the analysis simply hasn't run yet at that point.

## How do you restrict Post-Call Functions?

You can aggressively gate post-call functions from firing by setting strict conditional logic rules based on dynamic variables or call statuses.

In the function's configuration, you can deploy **Variables condition** rules (e.g., Only execute if `{{call_status}}` = `ended`). If a post-call function is gated off, any sequential functions that depend on it are instantly skipped as well.

* **Variables condition** — compare a `{{variable}}` against a value using `=`, `≠`, `>`, `<`, `≥`, `≤`, contains, not contains, exists, or not exists. Choosing exists or not exists removes the value field entirely, since there's nothing left to compare.
* **Disconnection reason** — specify one or more reasons the session must have ended with.
* **Call status** — require a particular final status.

A function with no rules set always runs. A function that gets gated off is treated as though it never ran, so anything depending on it gets skipped as well — usually exactly what you'd want: gate off the lookup, and the write that depends on it disappears right along with it.

## Examples

### Greeting an Identified Caller and Loading Their Tickets

A support line greets the caller by name and already has their open ticket in context.

**Pre-call functions:**

1. `find_user` — Zendesk **Search User**, with `phone_number` pinned to `{{user_number}}`. On the **Output** tab, the `id` field maps to `zendesk_user_id`, and `name` maps to `caller_name`.
2. `list_tickets` — Zendesk **List User Requested Tickets**, added as a *sequential* function under `find_user`, with `user_id` set to `{{zendesk_user_id}}`.

The prompt then opens with something like `Greet {{caller_name}} by name.`, and since the ticket list is already in context, "what's the status of my ticket?" gets answered on the very first turn instead of the third.

The exact same pair works just as well on a [chat agent](/build/create-chat-agent) as pre-chat functions — just swap `{{user_number}}` for whatever [dynamic variable](/build/dynamic-variables) your chat session starts with, such as an email address passed in when the widget first opens.

### Logging the Session and Opening a Follow-Up Task

A sales agent writes every conversation back into HubSpot, and only creates a task when there's actually something to follow up on.

**Pre-call function:**

* `search_contact` — HubSpot **Search Contact** using `{{user_number}}`, mapping the record ID to `hubspot_contact_id`.

**Post-call functions:**

1. `log_hubspot_call` — HubSpot **Log Call Activity** against `{{hubspot_contact_id}}`, with the body set to `{{call_summary}}`. Gated on **All**: `{{call_summary}}` exists — so a call that never got far enough to be analyzed writes nothing at all.
2. `create_followup` — HubSpot **Create Task**, added as a *parallel* function alongside `log_hubspot_call` so both writes fire off together. Gated on **All**: `{{call_status}}` = `ended` **and** `{{followup_needed}}` = `true`, where `followup_needed` is a custom [Post Call Extraction](/features/post-call-analysis-overview) field. Its subject line is a description the LLM fills in based on the transcript.

The session gets logged every single time it finishes; the task only shows up on the conversations that actually earned one.

### Confirming a Booking by Text

A clinic texts the caller after the call, but only when a booking genuinely happened.

**Post-call functions:**

1. `get_booking` — Cal.com **Get Booking**, with the UID set to `{{booking_uid}}`, a variable an in-conversation **Book Appointment** tool set earlier in the call. Gated on **All**: `{{booking_uid}}` exists.
2. `send_confirmation` — an **SMS** function, run sequentially under `get_booking`, whose content the LLM writes based on the transcript and the booking response.

If no booking happened, `{{booking_uid}}` was never set, the gate fails, and both functions get dropped, so no text goes out at all. On a chat agent, swap the SMS step for a **Custom function** that posts to your own notification endpoint instead.

## What are the timing limits and budgets?

Tavly imposes rigid timing budgets on workflow graphs to prevent infinite stalls. If a pre-call function massively breaches its time budget, the call still connects, but the agent's prompt simply lacks the delayed variable data.

| Phase | Execution Timing | Time Budget | Failure State |
| --- | --- | --- | --- |
| **Pre-Call (Inbound)** | Before agent speaks | 1 Minute | Call connects; data arrives too late for initial prompt. |
| **Pre-Call (Outbound)** | Before dial occurs | 5 Minutes | Dial initiates; data arrives too late for initial prompt. |
| **Pre-Chat** | Before chat opens | Infinite | N/A |
| **Post-Call/Chat** | After extraction ends | 5 Minutes | Remaining post-call functions instantly cancel. |


Going over that budget doesn't cancel anything — the remaining functions **keep running in the background**, and whatever they return still reaches the agent: every call and its response still get added to the transcript the LLM reads, and any variables they map remain available downstream, post-call functions included. What a late-arriving function misses is only the initial prompt and the agent's opening message, since those are already built by the time it finishes. So the time budget is really the deadline for anything the agent's opening words depend on — not a deadline for the data itself.

Post-call functions are capped at **5 minutes** total, and that limit is a hard stop — whatever hasn't finished by then simply gets cancelled so teardown can complete.

|                        | Pre-conversation                                                                                                                                             | Post-conversation                       |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| When it runs             | Before the agent's first message; for outbound calls, before Tavly even dials                                                                                       | After Post Call Extraction finishes       |
| Time budget (voice)      | 1 minute for inbound and web, 5 minutes for outbound                                                                                                                 | 5 minutes                                 |
| Time budget (chat)       | None — the chat simply waits for the graph to complete                                                                                                               | None                                      |
| Past the budget          | The session begins anyway; remaining functions finish quietly in the background and still reach the transcript, just too late for the opening prompt or greeting     | Remaining functions get cancelled          |
| Max functions            | 15                                                                                                                                                                     | 15                                         |
| Max chain depth          | 4                                                                                                                                                                      | 4                                          |

Figures reflect August 2026.

## When a Function Fails

A failure stays contained to the function where it happened. Whether a function errors out, times out, is missing a required input, or gets gated off, it's marked unsuccessful, and:

* **Everything that depends on it gets skipped**, along with everything that depends on those, in turn. A failed lookup takes down whatever write needed its ID, rather than firing off a request with a blank field.
* **Independent branches keep going regardless.** A failed CRM lookup doesn't stop a calendar check running alongside it.
* **The session still continues.** A pre-conversation failure doesn't stop the call from connecting or the chat from opening — it just proceeds without those particular variables, so it's worth writing your prompt to read sensibly when a lookup came back empty. A post-conversation failure still lets teardown finish normally.

## Reviewing What Ran

Open the call in [call and chat history](/features/session-history) and check the transcript. Pre-call function calls appear under a **Before call** divider at the very top, the conversation itself follows **Call started**, and post-call functions sit under **Call ended** at the bottom. Each entry shows both the arguments sent and the response received, making it easy to tell a bad input apart from a genuine provider error. During a live call, these same entries collapse under **Before conversation** in the live transcript view.

Chat sessions handle their pre-chat and post-chat functions exactly the same way.

## FAQ

<AccordionGroup>
  <Accordion title="Can the agent decide on its own not to run a pre-call function?">
    No. Every function in the slot runs automatically whenever its dependencies are satisfied. Unlike a tool used mid-conversation, there's no LLM decision involved about *whether* to call it — the LLM only gets involved in filling in inputs you've described rather than pinned outright, and post-conversation functions come with an **only when** gate that you control yourself.
  </Accordion>

  <Accordion title="Where does the LLM pull values from for described inputs, before the conversation has even started?">
    From the agent's prompt and whatever dynamic variables are available at that point, including outputs from earlier functions in the graph. Since there's no conversation yet, an input that can only ever come from something the user says belongs on an in-conversation tool instead. Post-conversation functions, by contrast, do have access to the full transcript.
  </Accordion>

  <Accordion title="Do pre-call functions delay the actual call?">
    Yes, for however long the graph takes — up to 1 minute on an inbound or web call, and a chat waits indefinitely for its pre-chat graph with no set budget at all. Outbound calls absorb their 5-minute budget before dialing even begins, so nobody ever hears the delay. It's worth keeping chains shallow: two functions running in parallel only cost as much as one function's latency, while two chained together cost the sum of both. If a slow lookup isn't actually needed for the opening line, it's better run as an in-conversation tool instead.
  </Accordion>

  <Accordion title="Can a post-call function read what a pre-call function returned earlier?">
    Yes. Pre-conversation outputs stay available as dynamic variables for the entire session, so a post-conversation function can reference them directly. That's exactly how the HubSpot example above reuses `{{hubspot_contact_id}}` instead of looking the contact up a second time.
  </Accordion>

  <Accordion title="What happens if two functions end up with the same name?">
    Saving gets rejected outright. Names are what other functions use to reference each other, so they need to be unique within a given slot. That said, the same name can appear once in the pre-conversation slot and once in the post-conversation slot without conflict.
  </Accordion>
</AccordionGroup>
