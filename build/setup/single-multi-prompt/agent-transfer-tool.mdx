## What is the Agent Transfer tool?

The **Agent Transfer** tool, also known as **agent swap**, transfers an active conversation between AI agents mid-call without disconnecting. The incoming agent instantly inherits the complete conversation transcript and session context, enabling modular call flows across specialized agents without initiating external phone transfers or asking callers to repeat previous statements.

Instead of routing a call through an external telephonic switchboard, Tavly executes an in-memory session swap. This capability lets you avoid monolithic prompt architectures by modularizing complex conversational workflows into targeted, single-purpose agents.

### Typical use cases

* **Intent-based routing:** Pass a caller from a front-desk receptionist agent to a booking-specific specialist once user intent is confirmed.
* **Language switching:** Transition seamlessly to an agent configured for a specific language based on the caller's spoken preference.
* **Modular agent architecture:** Keep each agent prompt compact and strictly focused on a single responsibility, chaining them sequentially (**A → B → C**) rather than maintaining an unwieldy prompt.

> *"Decomposing complex agent workflows into discrete, single-task sub-agents significantly reduces LLM hallucinations, lowers prompt token overhead, and guarantees higher execution accuracy across multi-step conversational journeys."*

## When should you use Agent Transfer?

You should use **Agent Transfer** when moving callers between **AI agents on the same call** to divide complex flows, switch spoken languages, or reuse modular agents. However, you must use traditional [call transfer](/build/setup/single-multi-prompt/transfer-call) if the destination is a human agent or external phone number, as Agent Transfer operates strictly within Tavly.

To guarantee that routing logic executes without errors, evaluate your handoff destination against the architectural boundaries detailed below.

### Supported vs. unsupported handoff targets

* **Within-platform AI agents:** Supported. Agent Transfer exclusively shifts control between configured Tavly AI voice agents.
* **Human agents & external phone numbers:** Unsupported via Agent Transfer. Use [call transfer](/build/setup/single-multi-prompt/transfer-call) to route calls out to a PSTN or SIP destination.
* **Agents with custom LLMs:** Incompatible. Destination agents running on a [custom LLM](/integrate-llm/overview) cannot be transfer targets; initiating a transfer to them will fail.
* **Chat-only agents:** Incompatible. Chat-channel agents cannot receive live voice handoffs; attempting this transfer will fail and keep the call on the original agent.

## How does Agent Transfer compare to Call Transfer?

**Agent Transfer** executes **instantaneous internal handoffs** without dialing new SIP endpoints, avoiding telephony failure risks and eliminating handoff scripts. Because both agents share the existing connection, destination agents do not require dedicated phone numbers. Unlike traditional phone-only transfers, Agent Transfer works identically across **telephony calls and web calls**.

The following comparison table breaks down the key technical and operational distinctions between an internal agent swap and a traditional telephonic call transfer:

| Feature / Architecture | Agent Transfer (`agent_swap`) | Traditional Call Transfer (`transfer_call`) |
| :--- | :--- | :--- |
| **Transfer Destination** | Native Tavly AI voice agent | Human agent, department, or external phone number |
| **Execution Latency** | **Near-instantaneous** (internal session swap) | Variable (carrier dialing, ringing, and bridge delay) |
| **Telephony Reliability** | **100% reliable** (no SIP legs initiated) | Dependent on carrier networks and line availability |
| **Context Retention** | **Full conversation transcript & context** inherited automatically | Requires handoff scripts, whisper announcements, or drops context |
| **Phone Number Overhead** | **1 phone number** serves an unlimited fleet of agents | Receiving endpoints typically require individual DIDs or extensions |
| **Supported Channels** | **Phone calls and web calls** | Phone calls (telephony PSTN/SIP) only |

## What session data carries over to the new agent?

During an **Agent Transfer**, the entire session retains the original `call_id` and persists as a unified log in [call history](/features/session-history). The destination agent automatically inherits the **complete conversation transcript**, all call-level **metadata**, and all **dynamic variables**, ensuring uninterrupted context without requiring manual variable mapping or custom parameter pass-through scripts.

Because the underlying call session remains intact throughout the handoff, the receiving agent automatically receives:

* **The full conversation transcript:** Every conversational turn spoken prior to the transfer is delivered to the receiving agent, giving it the exact context the caller experienced.
* **Call-level `metadata`:** Key-value pairs assigned during call initialization—such as parameters from [Create Phone Call](/api-references/create-phone-call) or the [Inbound Call Webhook](/deploy/inbound-call-webhook)—remain accessible across all participating agents.
* **Dynamic variables:** Both the system variables set at the start of the call (`retell_llm_dynamic_variables`) and values [extracted mid-call](/build/setup/single-multi-prompt/extract-dynamic-variables) persist seamlessly into the new agent prompt.

There is no dedicated "pass variables" toggle on the Agent Transfer tool because the shared session context propagates this data automatically. If you need the destination agent to act on specific mid-call information, use [Extract Dynamic Variable](/build/setup/single-multi-prompt/extract-dynamic-variables) on the source agent first, then reference it as `{{variable_name}}` inside the destination agent's prompt.

## What settings stay locked and what settings change?

During a transfer, **core compliance and audio configurations** remain locked to the primary agent that initiated the call, whereas **persona and execution settings** switch to the destination agent. You can optionally preserve the original voice or language across the transition to ensure vocal continuity without disrupting agent-specific prompts or tools.

Understanding the boundary between persistent call-level settings and agent-specific configurations ensures consistent compliance and audio fidelity:

| Setting Category | Persistent (Locked to First Agent) | Dynamic (Switches to Destination Agent) | Optional Overrides |
| :--- | :--- | :--- | :--- |
| **Call Security & Data** | Recording access (`opt_in_signed_url`), Data storage (`data_storage_setting`), PII redaction (`pii_config`) | None | None |
| **Audio Processing** | Telephony denoising mode | Ambient background sound | Preserving voice also preserves ambient sound |
| **Voice & Persona** | None | Agent voice, voice speed, spoken language | **Keep the same voice**, **Keep the current language** |
| **Agent Intelligence** | None | LLM model, system prompt, tool definitions, knowledge bases, boosted keywords, interruption sensitivity | None |
| **Event Webhooks** | Default webhook recipient | Inactive by default | Configurable: Source only, Destination only, or Both |

## How do you configure the Agent Transfer tool?

To configure **Agent Transfer**, add the tool under the agent's **Functions** menu, select your destination agent, and configure optional voice, language, extraction, or webhook settings. Finally, define an explicit conditional trigger within the agent's **system prompt** and validate the end-to-end handoff inside the Tavly testing playground before deploying live.

Follow these step-by-step instructions to enable agent swapping on single-prompt or multi-prompt agents:

<Steps>
  <Step title="Add the tool">
    Navigate to your agent configuration, locate the **Functions** section, click **+ Add**, and select **Agent Transfer** from the dropdown menu.

    </Frame>
  </Step>

  <Step title="Set the transfer options">
    Configure the transfer parameters within the modal:

    * **Select agent:** Choose the specific target agent to hand the call to. You can select a pinned version or specify **Latest** to ensure transfers always route to the currently published agent version. Unless overridden, the destination agent will use its own configured voice.
    * **Talk While Waiting (optional):** When enabled, the agent bridges execution pauses longer than roughly 2 seconds with a conversational filler phrase (e.g., *"Let me get you to the right person."*). You can supply a prompt instruction for the LLM to generate dynamically or provide a fixed phrase to read verbatim.
    * **Post Call Extraction setting:** Dictates which agent configuration manages [Post Call Extraction](/monitor/post-call-analysis-overview) upon call conclusion. Selecting **Only transferred agent** applies the destination agent's extraction schemas, fields, and prompts. Selecting **Both this agent and transferred agent** merges schema fields from both agents (destination fields override conflicts); running both schemas incurs additional analysis usage cost.
    * **Webhook setting:** Determines which endpoint receives post-transfer [webhook](/monitor/webhook-overview) lifecycle events: **Only this agent**, **Only transferred agent**, or **Both this agent and transferred agent**. By default, only the originating agent's webhook is triggered.
    * **Keep the same voice / keep the current language (optional):** Forces the destination agent to retain the originating agent's voice profile or language rather than defaulting to its own settings. Preserving the voice automatically maintains the active ambient background sound.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Can a call be transferred more than once, or sent back to a previous agent?">
    Yes. Every destination agent possesses its own independent toolset, including its own Agent Transfer tool. You can chain multiple transfers sequentially (**A → B → C**) or route the call back to an earlier agent in the chain. There is no hard platform limit on total transfers per call session; the only constraint is that a new transfer cannot initiate while another transfer is actively executing.
  </Accordion>

  <Accordion title="Will the caller notice the transfer happening?">
    Only if you configure the agent to announce it. The internal agent swap completes almost instantaneously within the same audio connection. If you want the agent to speak during the transition, enable **Speak during execution** (or **Talk While Waiting**) to deliver a natural handoff message.
  </Accordion>

  <Accordion title="Does a transfer generate a new call or call ID?">
    No. The call persists under the identical `call_id` and records as a single consolidated session in [call history](/features/session-history). All transcripts, custom metadata, and dynamic variables persist continuously throughout the swap.
  </Accordion>

  <Accordion title="How is this different from agentic warm transfer, which also involves a second AI agent?">
    They serve entirely different operational objectives, and the secondary AI agent interacts with different parties in each transfer type:

    * **Agent Transfer (`agent_swap`):** Replaces the active AI agent interacting directly with your caller. No outbound telephony call is placed—the conversation continues uninterrupted under the same `call_id` with full context inheritance.
    * **[Agentic warm transfer](/build/setup/single-multi-prompt/transfer-call):** Initiates a secondary outbound telephone call to an external phone number. The transfer agent speaks exclusively with the recipient at the destination while the original caller remains on hold.

    Once the transfer agent confirms the recipient is ready and bridges the call, both caller and recipient connect directly while all AI agents disconnect. In contrast, Agent Transfer ensures an AI agent remains active on the line at all times.
  </Accordion>

  <Accordion title="What kinds of agents can't be transfer destinations?">
    Agents built on a [custom LLM](/integrate-llm/overview) and chat-channel agents cannot serve as transfer destinations. Attempting an agent swap to either target will fail gracefully, allowing the active agent to maintain the conversation without dropping the call.
  </Accordion>

  <Accordion title="How does this tool show up in the API?">
    In the Tavly API, the tool `type` is `agent_swap`. It accepts an `agent_id` parameter and an optional `agent_version` (which defaults to the latest published agent version). Because the underlying LLM identifies the tool by its configured **name**, assign it a descriptive function name, such as `transfer_to_appointment_agent`.
  </Accordion>
</AccordionGroup>
