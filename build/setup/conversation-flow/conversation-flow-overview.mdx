# Conversation Flow Agents: Structured Control Over Voice AI Calls

> Build structured Tavly voice agents using conversation flow — a system of nodes for dialogue, tools, transfers, code execution, and transitions that gives you precise control over how a call unfolds.

## What Is a Conversation Flow Agent?

A conversation flow agent is built from multiple connected nodes, each handling a different part of the conversation. This gives you far more granular control over how a call proceeds compared to Single/Multi Prompt agents, making it possible to handle complicated scenarios while keeping the outcome predictable.

### Why Use One

* **Structured conversations** — define the exact paths a call can take and how it moves between them
* **Predictable behavior** — each node carries its own specific logic and produces a defined outcome
* **Support for complexity** — conditional branching and state management are built in
* **Room to fine-tune** — attach node-specific examples to sharpen performance

## What a Flow Is Made Of

* **Global Settings** — configuration that applies across the whole conversation:
  * The global prompt and overall personality
  * Default voice and language
  * Agent-wide parameters and behavior

* **[Node](/build/conversation-flow/node)** — the fundamental building block of a flow. Several node types exist:
  * Conversation nodes, for dialogue that doesn't call any tools
  * Subagent nodes, for dialogue that does call tools
  * Function nodes, for deterministic API and tool execution
  * Logic nodes, for branching
  * End nodes, for terminating the call

* **[Edge](/build/conversation-flow/transition-condition)** — the connections between nodes that define how the flow moves:
  * Transitions based on specific conditions
  * A default fallback path when no condition matches
  * Routing that adapts dynamically to the conversation

* **Tools / Functions** — reusable capabilities attached to subagent nodes, or triggered from function nodes. Conversation nodes don't use tools or functions at all:
  * Custom integrations with your own APIs
  * Built-in utilities like calendar actions, SMS, and transfers
  * Connections to external services

## How a Flow Runs

Each node carries a small, self-contained piece of logic, and a transition condition determines where the conversation goes next. The moment a condition evaluates true, the agent moves to the corresponding node. Nodes can also carry fine-tuning examples that sharpen how well the agent performs at that step. Building this out generally takes longer up front, since you're mapping every scenario you want covered — but once it's built, it's noticeably easier to maintain, and performance stays stable and consistent.

## Moving Between Agents and Subflows

At the top of the builder sits a **selector**, defaulting to **Main flow**. Use it to jump between everything currently open, each of which lives in its own tab:

* **Agents** — your primary agent (**Main flow**), plus any **transfer agents** opened from an [agentic warm transfer](/build/conversation-flow/call-transfer-node).
* **Subflows** — any [subflows](/build/conversation-flow/components) you've opened for editing.

You can jump back to **Main flow** whenever you like.

## Getting Started Quickly

From the Dashboard, create a new conversation flow agent and start from one of the pre-built templates. The Dashboard shows every option available to the agent, along with details on each and any latency implications, plus estimated latency and cost for the agent overall. Adjust the template to fit your needs — every change saves automatically.

## Sharing One Flow Across Multiple Agents

A conversation flow exists as its own standalone resource, identified by a `conversation_flow_id`, which an agent points to through its `response_engine`. Because of this, the same flow can be linked to more than one agent — useful for keeping a staging agent and a production agent in sync, or for running several language or channel variants off the same logic.

* From the dashboard: build the flow once, then when creating or editing any agent, select that existing flow as its response engine.
* Via the API: set the same `response_engine.conversation_flow_id` value on each agent when calling [Create Agent](/api-references/create-agent) or [Update Agent](/api-references/update-agent).
* Any edit you make to the flow affects every agent linked to it, so roll out changes carefully and test them on a non-production agent first.

Settings that live at the agent level — voice, language, webhook URL, data storage, Post Call Extraction, and similar — stay independent per agent, so two agents can share a flow while still differing in these areas.

## How Pricing Works

Because the model used can be overridden on a per-node basis, the cost of each call is calculated from:

* How much time was spent in each node (in seconds)
* That node's specific per-second model price
* The sum of these costs across every node the call passed through

This setup lets you control costs deliberately — using cheaper models for simple routing steps and reserving premium models for the parts of the conversation that actually need them.
