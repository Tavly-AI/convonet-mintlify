## What is a Transition Condition?

**Transition conditions** strictly dictate whether an active AI agent moves to a new conversational state, and exactly where it routes to if so. 

Every single edge leading out of a functional node mathematically pairs a condition with a destination node. The exact moment that condition is satisfied, the agent transitions. This mechanism provides the absolute finest degree of control over a conversation flow, and is precisely where aggressive testing matters most.

## What types of conditions exist?

There are two fundamental kinds of transition conditions: natural language Prompts and deterministic Equations.

* **Prompt:** A natural-language descriptive condition that the underlying LLM actively evaluates against the real-time conversation context.
* **Equation:** A strictly deterministic mathematical comparison executed against **[Dynamic Variables](/build/dynamic-variables)**. This involves **no LLM computation** whatsoever.

**Example Prompt Conditions:**
* `User said something about booking a meeting`
* `User claims to be over 18`
* `User said they lived in New York or Los Angeles`

**Example Equation Conditions:**
```text theme={"dark"}
- {{user_age}} > 18
- {{current_time}} > 9 AND {{current_time}} < 18
- {{user_location}} == "New York"
- {{name}} exists
```

<Note> **Variable Dependency:** Equation conditions strictly evaluate against pre-existing dynamic variables. If the agent learns something for the first time mid-call, you must use a prompt condition, or formally extract it first using an [Extract Dynamic Variable Node](/build/conversation-flow/extract-dv-node).</Note>

## What are special edge types?

Beyond standard prompt and equation checks, nodes can support advanced fallback and override edges.

* **Else Edge:** The strict fallback path. It fires exclusively when absolutely nothing else matches, guaranteeing the flow never fatally stalls. Use it carefully—any unexpected user turn will route through here.
* **Always Edge:** Transitions completely unconditionally the exact moment the user finishes responding, aggressively bypassing all logic evaluation.
* **Skip Response Edge:** Generated automatically when a node's **Skip Response** setting is enabled. The transition fires the exact moment the agent finishes speaking, without waiting for human input.

## In what order are conditions checked?

When a transition check initiates, the routing engine aggressively evaluates conditions in this strict, hierarchical order:

1. **Always Edge:** If present, transitions immediately. Nothing else is evaluated.
2. **Equation Conditions:** Evaluated deterministically top-to-bottom. The very first true equation wins instantly.
3. **Prompt Conditions:** If no equation matched, the LLM weighs every prompt condition simultaneously against any [Global Node](/build/conversation-flow/global-node) entry conditions. It picks the single best fit.
4. **Else Edge:** If no equations or prompts matched, the flow forcefully routes here.
5. **Stay:** If all checks fail and no Else edge exists, the agent remains in the current node.

**When do these checks run?**
* **Standard/Subagent Nodes:** Immediately after every single human turn.
* **Tool Nodes (Function, Code, MCP, Extract):** Immediately after the backend tool returns its payload.
* **Telephony Nodes (SMS, Transfer):** Immediately after the telephony action definitively succeeds or fails.
* **Logic Split Node:** Instantaneously upon node entry.

## How do you write equation syntax?

An equation condition can support up to 50 individual comparisons joined by strictly structural logic: **ANY** (OR logic) or **ALL** (AND logic).

| Operator | Evaluates | Core Behavior |
| --- | --- | --- |
| `==`, `!=` | Strings | Case-insensitive strict comparison. No numeric coercion (e.g., `"18"` != `"18.0"`). |
| `>`, `>=`, `<`, `<=` | Numbers | Standard math comparison. Invalid numbers gracefully evaluate to **false** instead of crashing. |
| `Contains`, `Not Contains` | Strings | Case-insensitive substring validation. |
| `exists`, `does not exist` | Variable | Validates if a dynamic variable is populated. Empty strings evaluate to `true` (exists). |

## How do you add and manage conditions?

You construct transition logic directly within the node's edge menu, stacking and reordering equations to strictly define routing priorities.

<Steps>
  <Step title="Add a new condition">
    Click the target node, hit the **+** button, and explicitly select **Prompt** or **Equation**.

  <Step title="Write the condition text">
    For prompts, simply type the natural language rule. For equations, construct the logical rows and aggressively toggle **ANY/ALL** to set the required structural threshold.

## How do you improve transition accuracy?

Ensure every condition makes contextual sense independently, without forcing the LLM to rely on the node's base instruction to fill in contextual gaps.

* **Poor:** `When they say yes`
* **Optimal:** `When the user indicates they want to book a meeting`

If a transition misfires, explicitly tighten the prompt condition to describe exactly what the user said, or aggressively deploy [Fine-Tune Examples](/build/conversation-flow/finetune-examples) to force the LLM to map raw transcripts to the correct routing decision.


## FAQ

<AccordionGroup>
  <Accordion title="What happens if the caller says something that fits none of the conditions?">
    The order runs like this: first, if a global node's condition matches, the agent moves there. If not, and the node has an else edge, the agent transitions through it. If neither applies, the agent simply stays in the current node and responds according to its instruction.
  </Accordion>

  <Accordion title="How can I review the transitions from a past call?">
    Open the call transcript in the history tab — it lays out every transition along with which node it moved from and to. Giving your nodes descriptive names makes this much easier to follow.
  </Accordion>

  <Accordion title="Is there a cap on how many transition conditions a node can have?">
    There's no limit on the number of conditions per node, though each individual equation condition can hold at most 50 equations. It's still worth keeping the list tight — the more prompt conditions a node carries, the harder it is for the LLM to reliably pick the right one.
  </Accordion>

  <Accordion title="Why did the agent transition to a node whose condition was never actually met?">
    Take a look at your [global prompt](/build/conversation-flow/global-setting) and node instructions for numbered labels like "PRIORITY 1," "Step 2," or "ATTEMPT 1." When the agent is choosing its next node, numbers appearing in lists like these can get mixed up with its actual transition options, causing a transition to fire even though the real condition was never satisfied. Renaming these to letters ("PRIORITY A") or descriptive labels ("New service intent") usually fixes it — the underlying instructions themselves don't need to change.
  </Accordion>
</AccordionGroup>
