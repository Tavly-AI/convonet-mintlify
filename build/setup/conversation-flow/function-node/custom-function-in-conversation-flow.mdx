## What is a custom function in conversation flow?

A **custom function** allows your conversation flow agent to trigger an external HTTP API during an active call and ingest the response to steer dialogue. Configured inside a function node, it bridges the LLM with your backend systems to look up real-time data, update databases, or trigger business operations mid-call.

> Add a custom function to a Tavly AI's conversation flow to call your external API mid-call. Configure method, URL, headers, parameters, and responses.

When executed, the agent pauses or transitions according to your node configuration, sends an HTTP request to your specified endpoint, and feeds the resulting output directly back to the language model. This capability enables dynamic, database-backed voice agents that interact with your enterprise infrastructure.

### Tool execution architecture

Depending on where your business logic resides, Tavly AI provides multiple node types to execute logic:

| Execution Method | Execution Environment | Best For | Endpoint Required |
| :--- | :--- | :--- | :--- |
| **Custom Function** | Your external server / API | Real-time database lookups, business actions, proprietary logic | **Yes** (Public URL) |
| [**Code Node**](/build/conversation-flow/code-node) | Tavly AI sandbox | Lightweight JavaScript calculations, text parsing, formatting | **No** (Hosted in sandbox) |
| [**Integration Tools**](/build/conversation-flow/integration-tools) | Third-party providers | Native CRM, calendar, and helpdesk actions | **No** (Direct provider integration) |

Custom functions run inside a [**function node**](/build/conversation-flow/function-node).

## When should you use a custom function?

Use a **custom function** whenever an agent requires **live external data**, needs to execute **backend actions**, or relies on **custom branching logic** during a call. If logic is self-contained without server access, use a **code node**; for native third-party CRM or calendar actions, use pre-built **integration tools** instead.

Reach for a custom function in scenarios such as:

* **Look up real-time data**: Retrieve active order status, open appointment slots, caller account details, or shipment tracking numbers.
* **Take an action in your backend**: Create a support ticket in your internal database, update user records, or dispatch booking confirmations.
* **Branch on your own logic**: Call an endpoint that evaluates business rules and returns structured instructions dictating where the conversation flow navigates next.

### Practical scenario: order status lookup

A retail support agent needs to inform callers about their delivery status:
1. You configure a `get_order_status` custom function pointing to `https://api.yourstore.com/orders`.
2. When a caller provides their order number, the agent invokes the function with that identifier as an argument.
3. Your API returns the order status, carrier, and estimated delivery date.
4. The conversation flow branches based on the response—speaking the status directly to the customer or escalating to a human representative if the order record cannot be found.

## How do you create and configure a custom function?

To configure a **custom function**, define an informative **name and description**, choose an **HTTP method** (GET, POST, PUT, PATCH, DELETE), and specify a publicly reachable **endpoint URL**. Optionally configure **timeouts** (1,000–600,000 ms), **request headers**, **query parameters**, **payload parameters** via JSON schema, and map response fields to **dynamic variables**.

When invoked, Tavly AI dispatches an HTTP request to your configured endpoint with the function name and arguments.

<Steps>
  <Step title="Name and describe it">
    Assign the function a unique **name** using alphanumeric characters and underscores (such as `get_order_status`), along with a detailed **description**. Because the LLM reads this description to decide whether and when to invoke the function, specify precisely what data it takes and what action it performs.

    </Frame>

    Configuration example:
    * **Name**: `get_user_details`
    * **Description**: `Get user details based on name and age`
  </Step>

  <Step title="Choose the HTTP method">
    Select the HTTP verb Tavly AI uses when calling your endpoint: **GET**, **POST**, **PUT**, **PATCH**, or **DELETE**. The setting defaults to **POST**.

    | HTTP Method | Request Body Included | Data Transmission |
    | :--- | :--- | :--- |
    | **POST**, **PUT**, **PATCH** | **Yes** (JSON body) | Full JSON payload including function name, call context, and args |
    | **GET**, **DELETE** | **No** | Values transmitted strictly as URL query parameters |
  </Step>

  <Step title="Add the endpoint URL">
    Enter the publicly reachable URL that Tavly AI calls to execute the function. 
    
    For network security, Tavly AI strictly blocks requests directed to **`localhost`**, **private IP ranges** (e.g., RFC 1918), and **cloud metadata addresses**. To test against a local development machine, expose your local service via a secure tunneling service such as ngrok.
  </Step>

  <Step title="Set a timeout (optional)">
    Specify the duration Tavly AI waits for your endpoint to respond, configured in milliseconds.
    * **Allowed range**: `1000` ms (1 second) to `600000` ms (10 minutes).
    * **Default timeout**: `120000` ms (2 minutes).

    If your service does not return within the allotted timeout window, the request terminates as failed, and the agent receives an error message (such as a timeout error) to handle within the flow. Automatic retries can be enabled with `max_retry` (see [Retries](#retries)).
  </Step>

  <Step title="Set request headers (optional)">
    Define static or dynamic HTTP headers sent with the request. Dynamic values can reference [dynamic variables](/build/dynamic-variables), such as an authorization bearer token passed as `{{token}}`.

    <Frame>
      <img src="https://mintcdn.com/retellai/32uO5g9DswfoJ9j7/images/custom-function/headers.png?fit=max&auto=format&n=32uO5g9DswfoJ9j7&q=85&s=44295c732912fcb1c3f29259e3f59609" alt="Request headers configuration with an Authorization header set to a dynamic variable" width="830" height="132" data-path="images/custom-function/headers.png" />
    </Frame>
  </Step>

  <Step title="Set query parameters (optional)">
    Specify key-value query parameters appended to the endpoint URL. Parameter values are applied directly and can contain [dynamic variables](/build/dynamic-variables). 
    
    *Note: Query parameters are never populated autonomously by the LLM. For LLM-extracted values, define request body parameters.*
  </Step>

  <Step title="Define parameters">
    For **POST**, **PATCH**, and **PUT** requests, define the schema for parameters injected into the request body using either the raw JSON schema editor or the visual form builder:
    * Properties containing a `description` are populated dynamically by the LLM based on conversation context.
    * Properties containing a `const` value are assigned static values or dynamic variable interpolations.

    #### Payload: args only
    * **Enabled (ON)**: The request body contains only the function arguments at the root level without wrapping metadata.
    * **Disabled (OFF)**: The body wraps arguments alongside metadata according to the standard [request spec](#what-are-the-request-and-response-specifications) (`name`, `call`, and `args`).

    <Tip>
      Enable **Payload: args only** whenever your downstream API expects an exact JSON schema matching your argument definitions without Tavly AI wrapper keys.
    </Tip>

    ```json theme={"dark"}
            },

              "const": "{{last_name}}"
            }
          }
        },
        "order_id": {
          "type": "number",
          "const": 1234
        }
      }
    }
    ```

### Troubleshooting validation errors

If a custom function configuration fails to save, the parameter schema is typically invalid. The most frequent cause is omitting `"type": "object"` at the top level of the JSON schema. Select one of the platform's pre-built template examples and customize the properties from that baseline.

## What are the request and response specifications?

Tavly AI dispatches requests containing an **HMAC-SHA256 signature**, the function **name**, argument payloads in **args**, and conversation context in **call**. Your server must return an HTTP **200–299 status code** with a response under **15,000 characters**. Requests time out after **120,000 ms** by default unless configured otherwise.

### Inbound request specification

When invoked, Tavly AI transmits an HTTP request with the following structure:

* **Headers**:
  * `X-TavlyAI-Signature`: An **HMAC-SHA256 signature** generated across the raw request body string, utilized to authenticate request provenance. See [Verification](#how-do-you-verify-that-requests-originate-from-tavly-ai).
  * `Content-Type: application/json`: Included for all POST, PUT, and PATCH methods.
* **Body** (JSON payload for POST, PUT, and PATCH):
  * `name`: The string name of the executed custom function.
  * `call`: The call object containing rich session metadata, current call status, and a full transcript up to the execution moment. Refer to [Get Call](/api-references/get-call) for the complete schema.
  * `args`: A JSON object holding the parameters collected and passed by the LLM or constants.

<Note>
  When **Payload: args only** is activated, the request body contains exclusively the `args` object—omitting `name` and `call`. Parse parameters directly from the root JSON object, and verify request signatures against that raw body string.
</Note>

### Execution retries and backoff

Configure `max_retry` to control automatic retry behavior following an invocation failure:
* **Value range**: `0` to `5` (defaults to `0`, meaning no retries).
* **Failure triggers**: Triggers on transport timeouts, network errors, and HTTP `4xx` or `5xx` error codes.
* **Retry schedule**: Implements **exponential backoff with randomized jitter** between successive attempts (backoff parameters are system-managed).
* **Timeout calculations**: Configured timeouts apply **per attempt**, rather than across the aggregate operation. The maximum theoretical latency is `timeout * (max_retry + 1) + aggregate_backoff_delays`. Only the response from the terminal attempt is returned to the agent.

<Warning>
  Because every retry re-executes the HTTP request, your downstream endpoint may receive duplicate invocations. Set `max_retry > 0` strictly on **idempotent endpoints**.
</Warning>

### Outbound response requirements

* **Status codes**: Return an HTTP status code between **`200` and `299`** to communicate a successful outcome.
* **Payload formats**: Endpoints may return plain strings, buffers, blobs, or JSON objects. All formats are stringified prior to LLM injection. However, **only JSON objects** support dynamic variable mapping.
* **Character limits**: Response bodies are capped at **15,000 characters** by default to protect context window limits. Contact Tavly AI support if your application requires a limit expansion.

## How do you verify that requests originate from Tavly AI?

To verify request authenticity, validate the **`X-TavlyAI-Signature`** header against your **raw request body** using HMAC-SHA256 and your **Tavly AI API key**. Never parse or re-serialize the body prior to validation, as modified whitespace breaks signatures. Alternatively, restrict inbound traffic to Tavly AI's static outbound IP address **`100.20.5.228`**.

For GET and DELETE requests where no body exists, supply an empty string `""` to the validation function.

<CodeGroup>
  ```javascript Node.js theme={"dark"}
  import { Tavly } from "tavly-sdk";
  import express from "express";

  const app = express();
  // CRITICAL: Intercept the unparsed raw buffer, not JSON.stringify(req.body)
  app.use(express.raw({ type: "application/json" }));

  app.post("/check-weather", async (req, res) => {
    const rawBody = req.body.toString("utf-8");
    const signature = req.headers["x-tavlyai-signature"] || req.headers["x-tavly-signature"];
    
    if (
      typeof signature !== "string" ||
      !(await Tavly.verify(rawBody, process.env.TAVLY_API_KEY, signature))
    ) {
      console.error("Invalid signature detected");
      return res.status(401).json({ message: "Unauthorized" });
    }

    const content = JSON.parse(rawBody);
    if (content.args.city === "New York") {
      return res.json("25f and sunny");
    }
    return res.json("20f and cloudy");
  });
  ```

  ```python Python theme={"dark"}
  import os
  import json
  from fastapi import FastAPI, Request
  from fastapi.responses import JSONResponse
  from tavly import Tavly

  app = FastAPI()
  tavly = Tavly(api_key=os.environ["TAVLY_API_KEY"])

  @app.post("/check-weather")
  async def check_weather(request: Request):
      raw_body = (await request.body()).decode("utf-8")
      signature = request.headers.get("X-TavlyAI-Signature") or request.headers.get("X-Tavly-Signature")
      
      valid_signature = tavly.verify(
          raw_body,
          api_key=os.environ["TAVLY_API_KEY"],
          signature=signature,
      )
      
      if not valid_signature:
          return JSONResponse(status_code=401, content={"message": "Unauthorized"})
          
      content = json.loads(raw_body)
      if content["args"]["city"] == "New York":
          return JSONResponse(status_code=200, content={"result": "25f and sunny"})
      return JSONResponse(status_code=200, content={"result": "20f and cloudy"})
  ```
</CodeGroup>

<Note>
  In addition to cryptographic signature validation, you can restrict firewall access to Tavly AI's outbound static IP address: **`100.20.5.228`**.
</Note>

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Why isn't my agent calling the function?">
    The agent decides when to call a function from its name, description, and the flow around the function node. Make the description specific about what the function does and when to use it, and make sure the flow reaches the node under the right conditions. Vague descriptions are the most common reason a function never fires.
  </Accordion>

  <Accordion title="What information about the call can my endpoint access?">
    Unless **Payload: args only** is on, the request body includes a `call` object with details like the call ID, agent ID, metadata, dynamic variables, and the transcript up to the moment the function is called. Use it for context — for example, to look up the caller by their `metadata` or a dynamic variable.
  </Accordion>

  <Accordion title="How do I send data back to the agent?">
    Return it in the response body. Everything you return is converted to a string and handed to the agent's LLM, so the flow can speak or branch on it right away. To reuse a specific value later in the call, map it to a dynamic variable with the response variables setting.
  </Accordion>

  <Accordion title="Does Tavly AI retry a failed custom function?">
    Only if you ask it to. By default (`max_retry` = 0) a custom function isn't retried — if the request fails or times out, the agent receives the error message (such as the HTTP status or a timeout error) and continues based on the flow. Set `max_retry` up to 5 to retry on failure with exponential backoff; because each retry repeats the request, only do this if your endpoint is idempotent. See [Retries](#execution-retries-and-backoff).
  </Accordion>

  <Accordion title="What happens if the user interrupts while a custom function is running?">
    The agent handles it like any interruption: it turns to answer the user, and any waiting or follow-up message for that call is skipped. The request to your endpoint is **not** cancelled, though — it runs to completion (up to the timeout), so any action it takes still happens and any response variables it returns are still saved. The result stays in the transcript, so the agent can still bring it up on a later turn; it just won't read it back right at that moment. Because the request still reaches your endpoint, make side-effecting actions like creating a ticket or charging a card idempotent so a repeat call is safe.
  </Accordion>

  <Accordion title="Why does signature verification fail?">
    Verify against the raw request body, not a re-serialized version. `JSON.stringify(req.body)` can reorder keys or change whitespace, which breaks the signature. Read the raw body (for example, with `express.raw`) and pass that exact string to the verify function.
  </Accordion>

  <Accordion title="Can I point a custom function at localhost or a private IP?">
    No. Tavly AI blocks requests to localhost, private IP ranges, and cloud metadata addresses to prevent server-side request forgery. Your endpoint must be publicly reachable — to test a local server, expose it with a tunneling service like ngrok.
  </Accordion>

  <Accordion title="Is there a size limit on the response?">
    Yes. The function result is capped at 15,000 characters by default before it reaches the LLM. Return only what the agent needs, and contact support if you need a higher limit.
  </Accordion>
</AccordionGroup>
