## What is a Code Node?

A **Code Node** seamlessly executes JavaScript instantaneously the moment a conversation flow enters it. You should reach for this node when you specifically require mathematical calculations, complex data formatting, or a lightweight HTTP lookup that doesn't justify provisioning an external backend server. 

The executing code maintains secure access to dynamic variables and call metadata, and it can explicitly save parsed fields from the returned payload for subsequent nodes to utilize.

For example, a Code Node might instantly normalize an appointment timestamp string, securely return an `appointment_label`, and immediately let the flow branch depending on whether that exact timestamp was logically valid.

If you are developing a single- or multi-prompt agent instead, refer to the [Code Tool Guide](/build/single-multi-prompt/code-tool).

## How does it compare to a Custom Function?

The Code Node runs internally within Tavly's secure sandbox, whereas a Custom Function dispatches external HTTP requests to your proprietary backend servers. 

| Feature | Code Node | Custom Function |
| --- | --- | --- |
| **Execution Environment** | JavaScript executing securely inside Tavly's sandbox | An outbound HTTP request to your proprietary backend server |
| **Trigger Logic** | Fires automatically the precise moment the flow enters the node | Fires automatically when the flow enters a [Function Node](/build/conversation-flow/function-node) |
| **Data Inputs** | Dynamic variables plus call/chat metadata | Payload parameters, dynamic variables, and request data |
| **Best For** | Formatting, internal calculations, and low-risk HTTP lookups | Authenticated API integrations and production-grade database workflows |
| **Max Code Size** | 20,000 characters | N/A |

<Warning> Reserve the Code Node strictly for execution logic that does not touch highly sensitive secrets. Dynamic variables and metadata are permanently stored in plaintext alongside the active call record. For anything explicitly involving robust authentication, credential management, or production database writes, natively deploy a [Custom Function](/build/conversation-flow/custom-function) on your own hardened backend.</Warning>

## How do you set up a Code Node?

Configuring the node involves dropping it onto the canvas, writing the required JavaScript execution logic, manually mapping the returned response variables, and securely testing the payload.

  <Step title="Add the node">

  </Step>

  <Step title="Open the editor">
    Actively select the node, then explicitly click **Open** situated under the **Code Configuration** header.
  </Step>

  <Step title="Write your JavaScript">
    Programmatically pull required values from the `dv` or `metadata` objects, and mandate that the execution block returns a strictly JSON-serializable object.

    ```javascript theme={"dark"}
    const start = new Date(dv.appointment_start);

    if (Number.isNaN(start.getTime())) {
      return { valid: false, error: "Invalid appointment_start" };
    }

    return {
      valid: true,
      appointment_label: start.toISOString()
    };
    ```
  </Step>

  <Step title="Map fields to dynamic variables">
    Navigate to **Store Fields as Variables** and carefully connect an outbound dynamic-variable name to an exact JSON path inside your return payload (e.g., explicitly map `appointment_label` to `appointment_label`).
  </Step>

  <Step title="Set execution behavior">
    In the node's settings panel, explicitly decide whether the AI agent should speak or aggressively play a typing sound while the code actively runs, and define whether the flow must deliberately wait for the code result before transitioning.
  </Step>

  <Step title="Test it">
    Input mock data under **Dynamic Variables** inside the editor, then definitively click **Run Code**. The execution result and explicit `console.log()` outputs will appear safely below the editor frame without touching the live production agent.
  </Step>
</Steps>

## What is the JavaScript runtime environment?

Code aggressively runs inside an isolated, secure QuickJS sandbox environment that fully supports top-level `await`, comprehensive HTTP request capabilities via `fetch()`, and distinct variable scoping. 

### `dv` — Dynamic Variables
[Dynamic variables](/build/dynamic-variables) explicitly surface as properties attached directly to the `dv` object. Every value housed under `dv` structurally comes through as a string literal.

```javascript theme={"dark"}
const customerName = dv.customer_name;
const callerNumber = dv.user_number;
```

<Note> You must explicitly reference variables via `dv.user_number` inside your JavaScript logic. The standard `{{...}}` templating syntax fundamentally does not function inside the code execution block.</Note>

### `metadata` — Call or Chat Metadata
You can natively read whatever metadata payload was initially passed when the [phone call](/api-references/create-phone-call) was dynamically created. Unlike `dv`, this structure can securely hold any valid JSON type, completely bypassing the rigid string limitation.

```javascript theme={"dark"}
const priority = metadata.priority_level;
```

### `fetch(url, options)` — Making HTTP Requests
The sandbox actively supports `fetch()` for issuing secure HTTP and HTTPS requests, comprehensive request methods, and data bodies. 

```javascript theme={"dark"}
const response = await fetch("https://api.zippopotam.us/us/90210");

if (!response.ok) {
  return { found: false, status: response.status };
}
const location = await response.json();
return {
  found: true,
  city: location.places[0]["place name"],
  state: location.places[0]["state abbreviation"]
};
```

Non-HTTP protocols are blocked, along with certain local, private, and platform-internal addresses. This isn't a full implementation of the browser Fetch API.

Requests made from a Code node's `fetch()` originate from `35.166.138.221`. If your API restricts inbound traffic by IP, allowlist `35.166.138.221/32`.

### `console.log()` — Output During Testing

`console.log()` can be used while testing — output shows up in the **Run Code** results, but it never appears in the live code result or in call logs.

```javascript theme={"dark"}
console.log("Customer:", dv.customer_name);
```

### Runtime Limits

| Limit                    | Value                                |
| -------------------------- | ---------------------------------------- |
| Code size                  | 20,000 characters                         |
| Timeout                    | 5–60 seconds; 30 seconds by default       |
| Result sent to the agent   | 15,000 characters by default              |
| Automatic retries          | None                                       |

Common JavaScript built-ins are available — `Array`, `Date`, `JSON`, `Map`, `Math`, `Promise`, `RegExp`, `Set`, and similar. Node.js modules, browser DOM APIs, `require`, `import`, and `Intl` are not.

## Mapping Response Variables

Response variables extract fields from your full return value and store them as dynamic variables. Given this return value:

```javascript theme={"dark"}
return {
  status: "confirmed",
  order: {
    id: "ord_123",
    items: [{ name: "Replacement filter" }]
  }
};
```

you could set up:

| Dynamic-variable name | Path to value          | Stored value           |
| ---------------------- | ------------------------ | -------------------------- |
| `order_status`          | `status`                 | `confirmed`                 |
| `order_id`              | `order.id`               | `ord_123`                   |
| `first_item_name`       | `order.items[0].name`    | `Replacement filter`        |

Whatever gets stored comes out as a string — objects and arrays are serialized to JSON strings. If a path doesn't exist, or resolves to `null`, Tavly quietly skips that variable rather than failing the whole execution.

Response-variable extraction always uses the full return value, even in cases where the result passed to the agent gets capped at 15,000 characters.

## Controlling When the Node Transitions

**Wait for Result** is on by default.

* **Enabled:** Tavly rigidly waits for the code execution to complete before checking the node's outbound transition conditions. This fully guarantees both the return value and explicitly mapped response variables are securely available to power subsequent routing logic.
* **Disabled:** The conversation flow dynamically transitions away immediately while the code continues executing in the background. Because of this, the final result payload may fundamentally not be ready in time for the very next sequential node.

## What configurations are available?

Code Nodes offer robust behavioral settings to rigidly configure execution timeouts, agent conversational fillers, and LLM overrides.
If **Talk While Waiting** is on, the agent delivers whatever prompt or static sentence you've configured before transitioning. Should the caller speak while the code is still running, the agent can still respond to that turn. Turning **Talk While Waiting** off only suppresses the node's own entry message — it has no effect on the agent's ability to respond if the caller interrupts.

For anything that confirms an action succeeded, base it on [transition conditions](/build/conversation-flow/transition-condition) that check the stored result fields, rather than relying on conversational context alone.

## Configure settings for code-node in Tavly

| Setting                    | Default        | Behavior                                                                                             |
| ---------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------- |
| **Timeout**                  | 30 seconds       | Cuts off execution somewhere between 5 and 60 seconds.                                                       |
| **Talk While Waiting**       | Off              | Speaks one generated or static sentence as the node begins.                                                  |
| **Play typing sound**        | Off              | Plays a typing sound while Tavly waits on the result — only relevant when **Wait for Result** is on.         |
| **Wait for Result**          | On               | Holds off on transitioning until the result comes back.                                                      |
| **Global Node**              | Off              | Allows other nodes to jump to this one without needing a direct edge.                                        |
| **LLM**                      | Flow default     | Optionally swaps in a different model for this node's generated speech and transition decisions.            |
| **Fine-tuning Examples**     | None             | Adds transition examples specific to this node.                                                              |

## Using the Code Node Safely

* Keep API keys, credentials, and other sensitive tokens out of your code, `dv`, and `metadata` entirely.
* Reserve `fetch()` for low-risk reads. Anything authenticated or state-changing should go through a custom function on your own backend instead.
* For routing decisions that really matter, always give the flow a safe else path — a timeout, a thrown error, or a sandbox failure won't retry automatically and won't extract any response variables.

## FAQ

<AccordionGroup>
  <Accordion title="Can I use npm packages or browser APIs here?">
    No. The sandbox doesn't support `require`, `import`, Node.js modules, browser DOM APIs, or `Intl`. Stick to the built-in JavaScript features and `fetch()`.
  </Accordion>

  <Accordion title="Can I reference built-in system variables from the code?">
    Runtime values show up as properties on `dv` — things like `dv.call_id`, `dv.user_number`, and `dv.agent_number` when they're relevant to the current session. Access them with `dv.name` syntax. The `{{...}}` template syntax doesn't work inside JavaScript.
  </Accordion>

  <Accordion title="What happens if the code errors out or times out?">
    Tavly marks that execution as failed, skips response-variable extraction, and won't retry automatically. Wrap anything that might fail in `try/catch` and return a structured fallback, something like `{ "ok": false, "error": "lookup failed" }`. For routing that matters, set up a safe else path as backup.
  </Accordion>

  <Accordion title="Why did the agent speak even though Talk While Waiting was off?">
    That setting only suppresses the node's own entry message. If the caller talks while the code is still running, that turn can still trigger a response from the agent before the code's result is even back. Base any success confirmation on a stored result field rather than on conversational context alone.
  </Accordion>

  <Accordion title="Does async/await work here?">
    Yes — top-level `await` is fully supported, including around `fetch()` calls.
  </Accordion>

  <Accordion title="Is there a cap on how much data comes back?">
    By default, up to 15,000 characters get sent to the agent. Response-variable extraction, though, works from the complete return value before that cap is applied.
  </Accordion>
</AccordionGroup>
