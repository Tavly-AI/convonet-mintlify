## What is a Call Transfer Node?

A **Call Transfer Node** strictly routes an active phone call to a different external phone number or SIP URI. The agent remains entirely silent while inside this specific node. 

If you want the agent to speak a transition phrase (e.g., `Let me transfer you right away`) before the handoff, you must securely place a standard Conversation Node directly before it with `Skip Response` enabled.

<Warning> **Telephony Only:** This node functions exclusively on physical phone calls using Tavly numbers or imported numbers. It inherently does not work on web-based calls.</Warning>

## How do you set up the destination?

You must explicitly define the target destination for the transfer, which can be a standard phone number, a SIP URI, or a dynamic variable resolved at runtime.

<Steps>
  <Step title="Set the destination address">
    Point the transfer strictly at one of the following formats:
    * **e.164 format** (e.g., `+1234567890`)
    * **SIP URI** shaped exactly like `sip:username@domain` (e.g., `sip:user@tavlyai.com`)
    * A **[Dynamic Variable](/build/dynamic-variables)** resolved natively during the call.
    
    <Frame>
      <img src="https://mintcdn.com/retellai/CusS6gidcUzaxvEx/images/cf/transfer-call-e164.png?fit=max&auto=format&n=CusS6gidcUzaxvEx&q=85&s=ba54ab3635ca7cd934d213eb68414143" width="1182" height="1098" data-path="images/cf/transfer-call-e164.png" />
    </Frame>

    <Note> SIP URIs fundamentally cannot carry authentication inline (e.g., `sip:user:password@domain`). If your destination requires authentication, use custom SIP headers or route to an authenticated proxy endpoint.</Note>
  </Step>
  
  <Step title="Add custom SIP headers (Optional)">
    Add custom outbound SIP headers (typically prefixed with `X-`) to actively pass session-specific data like user IDs or campaign codes to your VoIP endpoint.
    
    <Warning> Custom SIP headers are strictly preserved only when transferring directly to a SIP endpoint. They are aggressively stripped if the transfer targets a standard PSTN number.</Warning>
  </Step>

  <Step title="Set the ring duration (applies to all modes)">
    Use this slider to decide how long the destination should ring for this particular transfer.

    * Whatever you set here only applies to this one transfer.
    * Leave it unset, and it falls back to your agent-level ring duration setting.
    * This works the same way across cold, warm, and agentic warm transfers.

    <Frame>
      <img src="https://mintcdn.com/retellai/XoiOOpBkax1duk4y/images/cf/transfer-dial-timeout.png?fit=max&auto=format&n=XoiOOpBkax1duk4y&q=85&s=91457ca85cf9ece8067d8ef983eb1214" width="816" height="118" data-path="images/cf/transfer-dial-timeout.png" />
    </Frame>
  </Step>

  <Step title="Set caller ID (optional)">
    Decide which caller ID the transfer destination will see:

    1. **Tavly Agent's number** — the destination sees the Tavly agent's number.
    2. **User's Number** — the destination sees the caller's own number. Your telephony provider needs to support caller ID override for this to actually work.
       * Warm transfer uses SIP DIAL, setting the `from` and `P-Asserted-Identity` headers to the caller's number.
       * Cold transfer uses SIP REFER, and whether caller ID override works depends entirely on the telephony provider.
       * Tavly Twilio numbers support showing the caller's number on both warm and cold transfer; Tavly Telnyx numbers only support this via SIP REFER on cold transfer.
       * If override isn't supported, the transfer will fail.

    <Frame>
      <img height="700" src="https://mintcdn.com/retellai/_QrxQEoxP5f0zRlL/images/telephony/caller-id-setting.png?fit=max&auto=format&n=_QrxQEoxP5f0zRlL&q=85&s=6f73a184623714e31913189556b39f59" data-path="images/telephony/caller-id-setting.png" />
    </Frame>
  </Step>

  <Step title="Configure cold transfer settings">
    For cold transfer specifically, you can set:

    * **Cold transfer mode** — either `SIP INVITE` or `SIP REFER`.
    * SIP (Session Initiation Protocol) is the underlying signaling protocol used to set up and route VoIP calls.
    * **SIP INVITE** — the default method. It establishes or updates the active call path and then bridges the transfer, and lets you choose which caller ID to display.
    * **SIP REFER** — asks an endpoint to start a separate call to a third party to complete the handoff. Only use this if your telephony provider actually supports it; caller ID behavior depends on the provider's support and configuration.
    * **Caller ID behavior** — the "show transferee as caller" option only applies when the cold transfer mode is `SIP INVITE`.

    <Frame>
      <img src="https://mintcdn.com/retellai/CusS6gidcUzaxvEx/images/cf/cold-transfer-settings.png?fit=max&auto=format&n=CusS6gidcUzaxvEx&q=85&s=c94a233055d022b53239d625249633d8" width="794" height="1092" data-path="images/cf/cold-transfer-settings.png" />
    </Frame>
  </Step>

  <Step title="Configure warm transfer settings (non-agentic)">
    For a standard (non-agentic) warm transfer, you can configure:

    * **On-hold music** — what the caller hears while on hold. Defaults to a standard ringtone.
    * **Navigate IVR** — provide a prompt to help the agent work through the destination's IVR system, if there is one.
    * **Enable human detection** — when turned on, the agent checks for a human presence once the destination answers, and only connects the original caller once a human is confirmed.
    * **Auto-greet** — if enabled, the agent immediately says "Hello" as soon as the destination picks up, encouraging a response that makes human detection more reliable.
    * **Agent detection timeout** — the maximum time the agent will spend trying to confirm a human answered. The caller only gets connected if detection succeeds within this window; otherwise the transfer is marked as failed. Defaults to 30 seconds.
    * **Whisper message (optional)** — a message spoken privately to the destination before they're connected to the original caller.
    * **Three-way message (optional)** — a message spoken to both the destination and the original caller once they're connected.

    <Frame>
      <img height="700" src="https://mintcdn.com/retellai/_QrxQEoxP5f0zRlL/images/telephony/warm-transfer-settings.png?fit=max&auto=format&n=_QrxQEoxP5f0zRlL&q=85&s=d813bc6a8f2fdb7c3dbb1ae8b8078c4b" data-path="images/telephony/warm-transfer-settings.png" />
    </Frame>
  </Step>

  <Step title="Configure agentic warm transfer settings">
    In an agentic warm transfer, a second AI agent — the **transfer agent** — takes the handoff, talks with whoever answers at the destination, and decides whether to bridge your caller through or cancel. For this mode, you can configure:

    * **On-hold music** — what the original caller hears while the transfer agent works.
    * **Two-way conversation agent** — the specific transfer agent (and version) that talks to the destination and decides whether to bridge or cancel. See **Choosing or creating a transfer agent** below.
    * **Wait time for agent answer** — how long the transfer agent has to reach a decision.
    * **Action on timeout** — what happens if that time runs out: **Cancel transfer** (treated as a failed transfer) or **Bridge the transfer** (connect the caller regardless).
    * **Three-way ring tone** — while the transfer agent works the handoff, the original caller hears the selected ring tone or on-hold audio until the call is either bridged or canceled.
    * **Three-way message (optional)** — a message shared with both parties once the call bridges. Write it as a **Prompt** (instructions the agent turns into a sentence) or a **Static Sentence** (exact wording).

    <Frame>
      <img src="https://mintcdn.com/retellai/pYRxYvv70IUyhP6N/images/transfer-agents/cf-agentic-warm-transfer-settings.png?fit=max&auto=format&n=pYRxYvv70IUyhP6N&q=85&s=f85540d891b3f229365b7bf0ea2fbf82" width="786" height="1294" data-path="images/transfer-agents/cf-agentic-warm-transfer-settings.png" />
    </Frame>
  </Step>

  <Step title="Choose or create a transfer agent">
    A **transfer agent** is a dedicated AI agent whose only job is to handle agentic warm transfers — think of it as a teammate that picks up the handoff, talks with whoever's at the destination, and decides whether to connect your caller. Transfer agents live separately from your regular agents, so they won't clutter up your main agent list.

    **1. Open the picker.** Click the **Two-way conversation agent** selector — it reads "Transfer screening agent" until you've picked one — to bring up the **Select transfer agent** window.

    </Frame>

    **2. Pick an existing agent.** Use the search box to find one, click it to preview it on the right, then click **Confirm selection**.

    </Frame>

    **3. Or build a new one.** Click **Create new**, pick a type — **Single Prompt** (simplest, a single set of instructions) or **Conversation Flow** (a visual, step-by-step flow) — then click **Create**. The new transfer agent opens right away for setup, either in a tab inside the builder or a new browser tab, depending on the agent type.

    **4. Manage an existing transfer agent.** Hover over a selected agent and open its **⋯** menu to **Rename** it, lock it to a specific **Version** (otherwise it always tracks the latest), or **Delete** it. Deleting removes every version of the agent, and also removes it from any transfer that was using it.

    </Frame>
  </Step>

  <Step title="Add custom SIP headers (optional)">
    Add custom SIP headers for outbound calls. These headers — typically prefixed with `X-` — let you pass session-specific data, like user IDs or campaign codes, between VoIP endpoints. They're forwarded to your SIP provider as part of the SIP INVITE, making them useful for custom routing and tagging.

    <Warning>Custom SIP headers are only preserved when the call transfers directly to a SIP endpoint — they may get stripped if the transfer goes to a PSTN number instead.</Warning>

    <code>All header names must start with `X-` or must be `User-To-User` (case insensitive)</code>

    </Frame>
  </Step>
</Steps>

## When does the node transition?

The Call Transfer node transitions strictly when a transfer actively fails (e.g., timeout, rejection, or unsupported caller ID). A pre-built edge exists exclusively to handle this failure routing. 

If the transfer succeeds, the active call permanently leaves the current agent's control, meaning the node inherently never transitions forward to a success state.

<Note> **Custom on-hold music:** While the dashboard UI only offers basic preset ringtones, you can upload proprietary audio files via the backend `create-asset` API endpoint. Set `on_hold_music` to `custom` and explicitly pass the returned `custom_on_hold_music_asset_id` to dynamically play your own MP3 or WAV files during warm transfers.</Note>
