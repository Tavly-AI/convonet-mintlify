## What is a Subagent Node?

A **Subagent Node** seamlessly blends multi-turn dialogue with dynamic, on-the-fly tool execution. Rather than firing a tool automatically, the LLM evaluates the conversational context and intelligently decides if, and exactly when, an attached tool should be utilized.

If your workflow requires pure dialogue without any tool calling, deploy a standard [Conversation Node](/build/conversation-flow/conversation-node) instead.

For example, a customer-support agent might use a single subagent node to actively handle order inquiries—chatting normally with the caller, and only executing an order-lookup tool when the caller explicitly provides an order number. 

## How does tool execution work?

When a subagent node has tools successfully attached, the LLM natively processes both the node's foundational instructions and the explicit list of available tools. As the conversation progresses, the LLM actively infers when a tool call is warranted, dynamically gathers the necessary parameters, and executes the call.

* **Multiple tools:** A single subagent node can confidently hold multiple tools simultaneously.
* **Continuous dialogue:** The agent is fully capable of continuing the conversation while a tool executes silently in the background.
* **Contextual responses:** Whatever payload a tool securely returns is made instantly available to the LLM to contextually shape its next spoken response.

## How does it compare to a Function Node?

Subagent nodes and [Function Nodes](/build/conversation-flow/function-node) serve distinctly different architectural purposes within a conversation flow.

| Feature | Function Node | Subagent Node |
| --- | --- | --- |
| **Execution** | Deterministic — forcibly fires the moment the node is entered | LLM-driven — dynamically fires only when the LLM decides it is necessary |
| **Tools per node** | Strictly one | Multiple |
| **Conversation** | Natively incapable of dialogue | Fully supports multi-turn dialogue alongside tool execution |
| **Best for** | Actions that absolutely must always run (e.g., automated lookup on entry) | Actions heavily dependent on human conversational context |

**Reach for a Function Node** whenever you require guaranteed, deterministic execution at a rigid sequence step.
**Reach for a Subagent Node** when the LLM should autonomously decide whether a tool call is warranted based on natural dialogue.

## How do you attach tools?

Attaching tools requires selecting the target node, configuring the specific tool parameters, and actively updating the node's prompt to guide the LLM's execution logic.

<Steps>
  <Step title="Select the node">
    Click directly on a subagent node to bring up its configuration panel on the right side of the canvas.
  </Step>

  <Step title="Add a tool">
    Navigate to the **Tools** section, explicitly click **+ Add**, and select your required tool type from the dropdown menu.
  </Step>

  <Step title="Set it up">
    Configure the exact tool parameters according to its specific type.
  </Step>

  <Step title="Update the node's instruction">
    Revise the node's foundational prompt so the LLM definitively knows exactly when to reach for the tool. Note that subagent nodes strictly support dynamic LLM **Prompts**; static sentences are not available.

    ```text theme={"dark"}
    Help the user actively check their order status. If the user explicitly provides an order number, immediately use the available order lookup tool to retrieve the latest status.
    ```
  </Step>
</Steps>

## What tools can you attach?

You can directly attach a wide variety of native integrations, backend actions, and telephonic routing commands to any subagent node.

| Tool type | Core Capability |
| --- | --- |
| **[Custom Function](/build/conversation-flow/custom-function)** | Execute standard HTTP requests to your proprietary external APIs |
| **[Code Tool](/build/single-multi-prompt/code-tool)** | Natively execute JavaScript directly within Tavly's secure sandbox |
| **[Integration Tools](/build/conversation-flow/integration-tools)** | Trigger native actions on connected providers like HubSpot or Cal.com |
| **[End Call](/build/single-multi-prompt/end-call)** | Forcibly terminate the active call |
| **[Transfer Call](/build/single-multi-prompt/transfer-call)** | Route the call via SIP/PSTN to an external phone number |
| **[Transfer Agent](/build/single-multi-prompt/transfer-agent)** | Instantly hand off the active call to a different specialized AI agent |
| **[Press Digit](/build/single-multi-prompt/press-digit)** | Generate and dispatch telephonic DTMF tones |
| **[Send SMS](/build/single-multi-prompt/send-sms)** | Dispatch an automated text message |
| **[Extract Dynamic Variable](/build/single-multi-prompt/extract-dv)** | Securely pull explicitly defined data variables directly from the conversation |
| **[MCP Tool](/build/conversation-flow/mcp-node)** | Dynamically call natively hosted tools on a connected Model Context Protocol server |

## How do you control agent speech during execution?

You maintain total control over whether the agent speaks a filler sentence while an external tool executes, and whether it verbally acknowledges the tool's returning payload.

* **Speak During Execution:** Instruct the agent to speak a filler sentence (e.g., `One moment, let me check that`) while the tool actively runs. This is critical for tools with noticeable network latency to prevent awkward dead air. You can generate this line dynamically via prompt or securely lock it as a Static Sentence.
* **Speak After Execution:** (On by default). Actively hands conversational control back to the LLM the exact moment the tool's result resolves, allowing it to verbally summarize the data to the caller. Toggle this off strictly for silent, fire-and-forget backend actions.

## Controlling What the Agent Says During Execution

Every tool comes with settings governing what the agent says while it's running, and what it says once it's done.

### Speak During Execution

Turning this on has the agent say something while the tool is still running — something like `One moment, let me check that for you.` This is worth enabling whenever a tool might take more than a second, network latency included, so the agent doesn't go silent and feel unresponsive.

You get to choose how that message is generated:

* **Prompt** — the LLM composes the line dynamically from a description you give it.
* **Static Sentence** — the agent reads back exactly the text you write.

### Speak After Execution

With this on (which is the default), the agent hands control back to the LLM once the tool's result comes in, so it can comment on the outcome to the caller. Turn it off if you want the tool to run silently instead.

<Note>
  * **Speak During Execution** is available for: Custom Function, Code Tool, Integration Tool, End Call, Transfer Call, Transfer Agent, Send SMS, and MCP Tool.
  * **Speak After Execution** is available for: Custom Function, Code Tool, and MCP Tool.
</Note>

## When the Node Transitions

* Once the caller finishes speaking, following the [evaluation order](/build/conversation-flow/transition-condition#evaluation-order).
* Immediately, if **Skip Response** is enabled — the moment the agent stops talking.

Since tool calls happen inside the subagent node itself, the node can remain active across multiple turns and multiple tool calls before it finally moves on.

## What node settings are available?

Subagent nodes offer advanced settings to tightly configure speech dynamics, model overrides, and edge routing.

* **Skip Response:** Restricts the active node to a singular edge that fires instantaneously the exact moment the agent finishes speaking.
* **Knowledge Base:** Actively attach a node-specific knowledge base that aggressively layers on top of the agent's global configurations.
* **Global Node:** Transforms the subagent into a universally reachable destination from anywhere else within the overarching flow.
* **LLM Override:** Explicitly assign a different underlying LLM exclusively for this specific node.
* **Speech Overrides:** Explicitly override global parameters exclusively for this node: Interruption sensitivity (0–1), Response wait time (0–5.5s), Voice speed (0.5–2), and DTMF Interruption capabilities.
* **Fine-tuning examples:** Actively inject sample transcripts to rapidly sharpen how this exact node decides on transitions and triggers tools.

## Best Practices

* **Be explicit in the node's instruction.** Spell out exactly when each tool should come into play.
* **Rely on function nodes for guaranteed execution.** If a tool absolutely has to run at a specific point in the flow, use a [function node](/build/conversation-flow/function-node) there instead.
* **Don't overload a single subagent node with tools.** There's no hard cap, but the more options the LLM has to choose from, the more likely it is to pick the wrong one. Spread tools across multiple subagent nodes instead.
