## Why does Prompt Architecture matter?

Prompt design dictates how your Tavly agent parses conversational history, routes dialogue logic, and executes tools. A highly structured, modular prompt guarantees that the underlying LLM makes predictable, deterministic decisions across diverse caller scenarios.

<Note> **Global Applicability:** These rules apply everywhere. In **Single Prompt Agents**, inject these structures into your root prompt. In **Conversation Flow Agents**, apply these guidelines to the specific system instructions of each individual node.</Note>

## How should you layout your prompt?

You must avoid monolithic walls of text. Segmenting your prompt into modular, clearly defined Markdown sections aggressively improves LLM execution accuracy, reduces prompt leakage, and allows you to share brand personas across multiple agents.

### Standard Section Layout
Organize your prompt using explicit Markdown headers to isolate behavioral rules:

```markdown theme={"dark"}
## Agent Persona
You operate as a voice representative for [Company Name].
Primary objective: [Define core task].
Domain knowledge: [List relevant products or systems].

## Conversational Constraints
- Keep replies brief: 1 to 2 sentences per turn unless detailing technical steps.
- Speak naturally: Use standard contractions and acknowledge incoming caller statements.
- Maintain professional patience: Acknowledge caller difficulties calmly.

## Spoken Output Standards
- Speak dates in full word form: Say "March fourth" instead of "3/4".
- Limit prompts to one query per turn: Do not combine questions.
- Mirror critical parameters: Restate important account numbers or names to verify accuracy.

## Workflow Execution
[Step-by-step procedure the agent must execute during the call]

## Handling Disruption and Resistance
- When the caller declines assistance: "Understood. Before we disconnect, is there another item..."
- When the caller expresses irritation: "I recognize the difficulty here. Let me address this immediately..."
```

## When should you scale to Conversation Flow?

Complex conversational trees rapidly degrade LLM reliability when forced into a single prompt. If your agent requires deep conditional logic, you must migrate to a node-based **Conversation Flow** architecture.

**Migration Triggers:**
Transition your agent to a Conversation Flow if it hits any of the following complexity thresholds:
* Requires **3 to 4+** distinct branching conditional paths.
* Interfaces with **5 or more** distinct external tools or integrations.
* Must track and persist multiple operational variables across consecutive turns.
* Consistently hallucinates or fails edge-case routing within a single prompt.

| Capability | Single/Multi Prompt | Conversation Flow |
| :--- | :--- | :--- |
| **Execution Scope** | Single prompt handles full dialogue tree | Each node targets a single isolated action |
| **Tool Execution** | Prompt-driven probabilistic routing | Deterministic execution per node setup |
| **Debugging** | Whole-prompt iteration | Discrete step testing and optimization |
| **Logic Control** | Inferred state tracking | Explicit state graphs and transitions |

## How do you orchestrate Tool Execution?

Language models routinely fail to execute tools accurately if they only rely on the API schema description. You must explicitly define exact trigger phrases, sequencing rules, and negative constraints directly in your prompt text.

<Note> **Architecture Note:** This orchestration guide applies specifically to Single/Multi Prompt Agents. Conversation Flow Agents execute their tools deterministically via node-level configurations.</Note>

### The 4 Rules of Explicit Orchestration
1. **Explicit Triggers:** Hardcode the exact user keywords that mandate a function call.
2. **Deterministic Order:** explicitly define prerequisites (e.g., "Always collect Account ID before calling `check_status`").
3. **Negative Constraints:** Define the exact edge cases where a tool must *never* run.
4. **Functional Purpose:** Tell the LLM *why* the tool exists so it understands the strategic value of the output.

### Orchestration Pattern Example

```markdown theme={"dark"}
## Tool Invocation Protocol

1. Collect caller details:
   - Obtain caller name and account identifier before triggering ANY queries.

2. Route by user intent:
   - When the user asks for a refund or disputed charge:
     -> Run `transfer_to_support` without additional queries.
   - When the user asks for shipment or delivery tracking:
     -> Run `check_order_status` using the provided order_id.
   - When the user requests an item change or order update:
     -> First run `check_order_status` to verify state.
     -> Then transition to modification_state.

3. Post-execution response:
   - Report the retrieved data back to the caller clearly.
   - Confirm whether the caller requires follow-up actions.
   - Process the next step only after confirmation.
```
