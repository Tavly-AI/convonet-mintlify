## What is the Tavly outbound calling system?

The **Tavly outbound calling system** enables organizations to initiate autonomous telephone calls powered by conversational AI voice agents. By binding configured agents to provisioned or imported telephone numbers, developers trigger high-fidelity outbound calls programmatically through REST APIs or directly from the dashboard for notifications, appointment reminders, and lead outreach.

Outbound calling operates with low audio latency and natural turn-taking over global carrier networks:

* **Trigger programmatically**: Launch calls dynamically from backend services or CRMs using REST endpoints.
* **Launch from dashboard**: Place instant manual test calls or outbound follow-ups directly through the console interface.
* **Per-call overrides**: Adapt agent prompts, voices, and dynamic variables per customer interaction without altering underlying agent templates.

### Prerequisites

* **Phone Number**: A [Tavly-managed or imported phone number](/deploy/purchase-number).
* **Agent**: A configured [conversational voice agent](/build/overview) ready for outbound conversations.
* **API Key**: An active Tavly API key for secure request authentication.

## How do you bind agents to phone numbers?

To **bind agents to phone numbers**, navigate to the Phone Numbers section in the Tavly dashboard, select your provisioned number, and assign dedicated inbound and outbound voice agents. This decoupling allows teams to utilize distinct specialized agents for incoming customer support callbacks versus outbound sales or notification campaigns.

### Configuration Roles

| Role | Operational Purpose | Representative Use Cases |
| :--- | :--- | :--- |
| **Inbound Agent** | Answers and handles incoming customer calls to this number | Customer support lines, inbound inquiries, callbacks |
| **Outbound Agent** | Assigned when initiating calls from this number | Sales development, proactive alerts, appointment reminders |

### Flexible Agent Assignment Options

* **Specialized Role Separation**: Assign different agents to handle inbound versus outbound legs independently.
* **Outbound-Only Numbers**: Leave the inbound agent unassigned to prevent incoming callbacks on broadcast-only lines.
* **Inbound-Only Numbers**: Configure solely the inbound agent for dedicated toll-free or support receiving lines.
* **A/B Split Testing**: Evaluate performance variations between agent prompts via [A/B Testing](/deploy/ab-testing).

## How do you make outbound calls programmatically via API?

To **make outbound calls programmatically via API**, issue an authenticated POST request to the Create Phone Call endpoint containing your verified E.164 from and to numbers. Developers can optionally specify agent overrides, inject dynamic prompt variables, attach tracking metadata, and transmit custom outbound SIP headers.

### Outbound Call Parameters

When initiating outbound calls (v2 API), configure the following payload parameters:

| Parameter | Type | Example | Description |
| :--- | :--- | :--- | :--- |
| `from_number` | string (E.164) | `+14157774444` | Your Tavly-managed or imported carrier telephone number. |
| `to_number` | string (E.164) | `+12137774445` | Destination party phone number in canonical format. |
| `override_agent_id` | string | `agent_abc123` | Override the default agent bound to the number (optional). |
| `override_agent_version` | integer | `1` | Specific version of the override agent (defaults to latest). |
| `agent_override` | object | See reference | Partial property overrides (voice speed, backchanneling, LLM settings). |
| `metadata` | object | `{"customer_id": "123"}` | Arbitrary key-value metadata saved with call records. |
| `retell_llm_dynamic_variables` | object | `{"name": "John"}` | Key-value strings injected dynamically into agent prompts. |
| `custom_sip_headers` | object | `{"X-Call-ID": "123"}` | Custom [SIP headers](/build/telephony/sip-headers) relayed to carrier trunks. |
| `ignore_e164_validation` | boolean | `false` | Bypass E.164 verification for custom telephony routing scenarios. |

<Warning>
  **Tavly-purchased numbers**: Tavly supports dialing to [15 international destinations](/deploy/international-call).  
  **Imported numbers**: International calling permissions depend on your external carrier trunk configuration.
</Warning>

  ```python Python theme={"dark"}

  from tavly import TavlyClient

  )
  ```

## How do you configure and scale CPS limits?

To **configure and scale CPS limits**, adjust your account calls-per-second thresholds to regulate how many outbound calls initiate concurrently each second. While Twilio supports up to 5 CPS and Telnyx scales to 16 CPS, custom SIP trunks can handle up to 150 CPS depending on carrier network capacity.

Calls Per Second (CPS) governs the dispatch velocity of newly established phone calls.

### Provider CPS Scaling Matrix

| Telephony Provider | Default CPS | Maximum CPS | Propagation Behavior |
| :--- | :--- | :--- | :--- |
| **Twilio** | 1 | 5 | Updates take up to 10 minutes to propagate |
| **Telnyx** | 1 | 16 | Updates apply instantly |
| **Custom Telephony** | 1 | 150 | Depends entirely on custom carrier SIP trunk throughput |

### Critical CPS Considerations

1. **Throttling Protection**: Calls triggered in excess of your configured CPS threshold will be rejected with rate limit errors.
2. **Gradual Scaling**: Scale dispatch velocity progressively in staging before launching high-volume campaigns.
3. **Carrier Constraints**: Upstream telephony providers enforce independent rate ceilings.
4. **Concurrency vs. CPS**: CPS controls dispatch velocity; total active simultaneous calls are capped separately by your [concurrency limit](/deploy/concurrency).

### Production Retry Strategy

<Tip>
  Implement exponential backoff retry algorithms to gracefully manage rate-limiting thresholds:

  ```javascript theme={"dark"}
  async function dispatchCallWithRetry(callPayload, maxRetries = 3) {
    let delay = 1000; // 1 second base delay
    for (let attempt = 0; attempt < maxRetries; attempt++) {
      try {
        return await tavly.call.createPhoneCall(callPayload);
      } catch (error) {
        if (error.code === 'rate_limited' && attempt < maxRetries - 1) {
          await new Promise((resolve) => setTimeout(resolve, delay));
          delay *= 2; // Exponential backoff multiplier
          continue;
        }
        throw error;
      }
    }
  }
  ```
</Tip>

## How do you monitor outbound call details and performance?

To **monitor outbound call details and performance**, subscribe to real-time webhook events or poll the Get Call API to retrieve conversation recordings, transcripts, latency metrics, and execution logs. Webhooks provide instant notifications when calls connect, conclude, analyze, or fail, facilitating automated CRM updates and performance tracking.

### Monitoring Channels

#### 1. REST API Polling

Execute the [Get Call API](/api-references/get-call) using the returned `call_id` to retrieve:

* Full conversation transcripts with timestamped speaker turns
* Stereophonic call audio recordings (`.wav` format)
* Turn-by-turn latency metrics and response engine execution times
* Tool invocation logs and structured data extractions
* Disconnection reasons and network termination codes

#### 2. Real-Time Webhooks

Register endpoints via [webhooks overview](/monitor/webhook-overview) to receive automated POST payloads for call lifecycle events:

* **Call Started**: Dispatched when media negotiation completes and the callee answers.
* **Call Ended**: Delivered upon call termination with final duration and disconnect cause.
* **Call Analyzed**: Emitted when transcription, sentiment analysis, and evaluation metrics are computed.
* **Call Failed**: Contains error status codes when connection attempts fail.

<Note>
  Webhooks eliminate polling overhead, ensuring your downstream systems update with minimal latency.
</Note>
